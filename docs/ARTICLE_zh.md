# agent 工具的 A/B 怎麼量才不會騙到自己

一個內部案例：我們把模型換成什麼都不做的 NOOP 假模型，跑同一組題目，照樣得到 12/12（各路線成績總對照，2026-10-19）。這代表那組題目的分數有一部分根本不是模型量出來的，評分器沒校準。我們做 AI agent 的工程工具，八個月內量過很多次「這個工具讓模型變強」。2026-10-19 回頭做校準稽核，結論很難看：2/20 到當天，所有宣稱「有提升」的數字，校準後都站不住；宣稱「沒提升」的大多是準的（量測校準稽核，2026-10-19）。紀錄都是真的跑過，錯的是量法，不是捏造（同上）。

這就是這篇要談的問題：你說「好了」「變強了」，憑什麼相信自己。這篇寫我們怎麼被騙、之後加了哪些檢查。

## 一、我們怎麼被自己的數字騙了

**1. 手寫答案只給一組。** 4–5 月的 A/B 出現 24/24 對 5–16/24 的大勝。開發 agent 逐題手寫答案函式，從 4/23 的 7 個長到 5/14 的 36 個，只有受測工具那組用得到，還被算成解題。5/20 那次每列只花 0.9 秒、有效 token 0/24，原始資料也沒留下（量測校準稽核，2026-10-19）。2026-10-16 把模型換成不做事的 NOOP 假模型跑同一題組，照樣 12/12（各路線成績總對照，2026-10-19）。

**2. 隱藏測試的結果只回饋給一組。** 同一批評測裡，只有受測工具那組拿到隱藏測試回饋；7/11 的一場，也只有它能重試，結論「沒提升、慢 3.6 倍」因此只算部分準確（量測校準稽核，2026-10-19）。

**3. 題目被調過。** 同樣 12 題反覆跑 ≥10 次，邊跑邊改。出題的人就是調程式的人，後來真正沒看過的保留題只剩 12 題，只看得出 ±25 個百分點的大差距（量測校準稽核，2026-10-19）。

**4. 評分錯。** 6 月的 85.7% 是腳本寫死：裸組被寫死只能解 2 題，驗證寫成 `if True`，模型根本沒被呼叫。9/29 的混合實驗 23/24 對 16/24，標準答案是受測程式自己產生的；照事先封存的規則重算，是 8/8 對 8/8（量測校準稽核，2026-10-19）。7/29 的三組校準裡，Nexus 組的 prompt 直接寫了答案（同上）。

**5. 公平 A/B，但受測能力全關。** 2026-10-14 終於做了條件對稱的同模型 A/B：P16 為 12/24 對 11/24，hard_v1 為 12/20 對 13/20，44 組裡 42 組結果相同，工具那組多用約 24% token，判平手（各路線成績總對照，2026-10-19）。但為了公平，工具的能力都被關掉：44 列自動修復 0、記憶命中 0、題目又設計成「看得到的測試會過」，所以永遠不會升級（量測校準稽核，2026-10-19）。這場平手量到的是「沒接好線」，不是「沒幫助」。然後我們把它講成「沒用」，是反方向的失準（同上）。

**6. A2 與 A0′ 的起點混淆。** 第三輪預註冊想把「回饋的效果」和「多抽一次的效果」分開。A2 從「base＋第一次 patch」續修並帶失敗回饋，對照組 A0′ 卻從 base 重抽，等於同時改了兩個變因。10/23 議會審查指出這點，結論：Gemini 輪的 A2 − A0′ 只能解讀成「整套重試策略」的效果，並寫進限制（第三輪預註冊，2026-10-22、議會共識，2026-10-23）。

**7. 分母不足卻下結論。** 4/26 的 54/54 對 51/54，只是 18 題各跑 3 次，差距全來自同一題的 3 次重複，不顯著（各路線成績總對照，2026-10-19）。R8 的子代理下放宣稱淨省率 47.68%，獨立稽核發現 302 檔（34.5%）子代理根本沒有目標檔案，腳本直接給它們 100% 召回；扣掉後覆蓋率 72.97%、淨省率 29.74%，低於 30% 門檻，由 WATCH 改判 DROP（R8 獨立稽核，2026-10-23）。第三輪也一樣：Sonnet 篩選 88 題只有 11 題合格，預估真錯不到 20 份（第三輪預註冊，2026-10-22）。

**8. 小效果疊加。** 記憶重播 76/101 對 BM25 基準 75/101，只多 +1.0 pp，事先的門檻是 +10 pp；向量檢索比零成本 BM25 多 +1.48 pp；向量重排檔案定位 +0.3 pp（記憶重測，2026-10-18、R7 離線驗證，2026-10-22、R6 離線閘門，2026-10-22）。每一個都只是一點點，加起來很像「持續進步」。我們靠的是每個機制各自對事先門檻判定、不加總。另一個提醒：BM25 檔案定位的 Hit@5 76.3%，其中 64.0 個百分點只是把 prompt 裡寫的路徑抄出來（R6 離線閘門，2026-10-22），基準線本身就要先拆開看。

## 二、每個陷阱對應的檢查

| 陷阱 | 檢查 | 出處 |
|---|---|---|
| 1、4 分數不是模型量出來的 | 另跑假模型臂，保留題必須 0 題通過；假模型的列若有非空 diff，整次作廢 | 量測校準稽核，2026-10-19；盲測保管作業規範 |
| 2、5 兩組資訊或能力不對稱 | 零模型 prompt diff：開跑前逐字比對兩組實際提示，只允許預先登記的差異（例：A0 與 A3 只差一段檔案清單，32/32 題確認） | 第二輪預註冊，2026-10-22；第三輪凍結紀錄 |
| 3 題目被調過、已曝光 | 題庫雜湊凍結；記每題修正日期與模型截止日並分層；請保管人比對曝光題庫；worker 看不到網址與修正後歷史 | 第二、三輪預註冊 |
| 4 評分器出錯 | 開跑前校準：參考解必須通過、「base＋一行註解」必須失敗 | 第三輪凍結紀錄（32/32 通過） |
| 5 能力全關 | 先證明接好線再量：逐列證明「有執行、有輸出、下游有用到」，沒過的不進量測 | 量測校準稽核，2026-10-19 |
| 6 起點不同 | 同起點分叉：對照臂與實驗臂從同一個 patch 起跑 | 議會共識，2026-10-23 |
| 7 分母不足 | 事先寫門檻與判定順序：先判「資訊不足」（分母 < 20），只報方向；不成立才分支持或未獲支持；凍結後不加題 | 第二、三輪預註冊 |
| 8 小效果疊加 | 每個機制事先設門檻（例 +10 pp），各自判定，不加總 | R6/R7 與記憶重測 |
| 事後改規則 | 凍結欄位；補遺只能在看到任何正式評分前提出 | 第三輪預註冊 |
| 自己量自己 | 做、量、批准分開；公開數字前由獨立者重算；解盲前先公布雜湊，解盲只一次 | 盲測保管作業規範；第二輪預註冊 |
| 偵測器自證 | 實作者自己寫的正例只算開發集：曾報「抓到 15/15」，盲寫的保留語料上是 53/120（44%） | 偵測器評估作業規範 |

補三點細節。**解盲要有閘門**：先公布候選集與分析報告的雜湊，再解盲；曾忘記先公布，事後補貼並註明遲了（盲測保管作業規範）。**事後發現的不對稱要標明事後**：某次盲測解盲後發現兩組的偵測器掃描範圍不同（NEXUS 33 筆、BARE 0 筆），題目文字本身是一樣的，處理方式是列為限制或敏感度分析，並標「事後」（盲測保管作業規範）。**操作者看了什麼要寫下來**：第三輪補遺 1 寫明，操作者為了判斷停點看過兩列的執行狀態欄位，沒有看 holdout 或任何評分（第三輪預註冊）。

## 三、一頁檢查清單

- [ ] 凍結：題集、測試、提示範本、模型版本、harness commit 都有雜湊，開跑後不改。
- [ ] 零模型 prompt diff：兩組提示逐字比對，只剩預先登記的差異。
- [ ] 假模型臂：保留題 0 題通過。
- [ ] 分數來自模型：沒有寫死答案、沒有不呼叫模型的捷徑。
- [ ] 兩組資訊對稱：隱藏測試回饋、重試次數、工具權限一樣。
- [ ] 受測能力真的有跑（有執行、有輸出、下游有用到）。
- [ ] 評分器校準：參考解過、已知錯誤解不過。
- [ ] 題目沒看過：不是調程式的人出的；曝光與模型截止日分層報告。
- [ ] 對照臂與實驗臂同起點，一次只改一個變因。
- [ ] 分母門檻與有順序的判定事先寫好：先判「資訊不足」，才分「支持」或「本期未獲支持」；凍結後不加題。
- [ ] 每個機制各自對門檻判定，小效果不加總；基準線先拆開看。
- [ ] 評分者看不到組別；先公布雜湊，再一次解盲。
- [ ] 補遺只在看到任何正式評分前提出，並記錄誰看過什麼。
- [ ] 做、量、批准分開；公開前獨立重算。
- [ ] 報告只寫量到的，沒量到的寫「本期未獲支持」。

## 四、我們現在怎麼做

同樣的問題也出現在「完成」這件事上。2026-10-17 對 11 個 repo、2,018 張已合併 PR 的稽核，確認「宣稱完成、其實沒完成」的下限是 133/2,018 = 6.6%（區間 5.6–7.8），推估 7–10%。治理規則訂得多嚴，跟這個比例看不出關係；抓到它們的是真實使用 54 件、獨立審查 27 件，自動閘門幾乎是 0（假完成稽核，2026-10-17）。

這些檢查現在是 Cairnwork 的量測做法。Cairnwork 是我們從 Nexus 轉出來的 AI 寫程式代理人交付驗證層，核心價值不是提高成功率，而是「完成有證據」（cairnwork README「定位」節）。它的 A/B 沿用上面的規則，第三輪預註冊的樣子：同一題、同一模型只跑一次，產生的 patch 同時用不同政策評估，每份 patch 不論是否交付都完整評分，才量得到誤擋；測試由三個互相看不到的作者寫；凍結紀錄寫下雜湊、種子、模型版本；Gemini 的真錯分母預估不到 20，所以預先寫明只報方向、不下結論（第三輪預註冊，2026-10-22）。

第二輪的結果提醒我們不要自滿：兩組交付精確率都是 42.9%（12/28），延後驗收 28/28 全放行，沒有擋下任何一筆，也就是 16 筆不可採用的交付全部漏攔（第二輪結果，2026-10-22）。細看這 16 筆：5 筆是 holdout 失敗，但都是同一個疑為評分環境副作用的回歸測試；11 筆通過 holdout，卻被兩位盲審判「需修改」，那是程式品質或風格問題，延後測試本來就不管。真正的 holdout 功能測試失敗，A0 只有 1 筆、A1 是 0 筆（同上）。所以這一輪的結論是：這批題裡幾乎沒有東西需要過濾，過濾的價值沒量到，也不是被否定。

10/23 的議會結論是：這個 A/B 只量到「延後隱藏測試這個過濾器」，量不到「完成有證據」（議會共識，2026-10-23）。攔錯、證據可信、收件方受益是三個問題，一個達標不能替另外兩個過關（同上）。另一個獨立的量測（擋錯能力量測）則顯示：Haiku 實跑 89 題只錯 6 題，小 bug 上模型本來就很少犯功能錯誤，交付前把關對小 bug 主要是保險，不是提升成功率（擋錯能力量測，2026-10-22）。這是另一批量測的結論，不能拿來解釋第二輪那 16 筆。

所以接下來加兩個不用 worker 額度的實驗：收件實驗（重用已評分的 patch，對照組是 PR diff 加普通公開 CI，實驗組是 diff 加範圍鎖定與離線驗簽的收據，不放逐題寫好的隱藏測試結果，否則量到的是「有人先寫好答案卷」），以及防假完成壓力測試（離線重放歷史假完成與人工偷改測試的 patch）。判定規則寫成建議稿：分母仍不足就承認主張不成立、改方向，不延賽（議會共識，2026-10-23）。

如果你也在做會讓 agent 或 AI PR「交付」東西的工具，歡迎看 Cairnwork；它怎麼擋、擋不住什麼，都用上面這套規則量，結果不論好壞公開。
